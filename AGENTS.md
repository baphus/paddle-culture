# AGENTS.md — paddle-culture

Single-package Next.js 16 app (npm, `package-lock.json`). No workspaces, no CI. See `README.md` for the human-facing overview.

## Commands

- `npm run dev` / `npm run build` (`next build`) / `npm start`
- `npx tsc --noEmit` — the only static check (`strict`, `noEmit`, `@/*` → `./src/*`)
- `npm test` — `node --test --import ./test/register-loader.mjs "test/*.test.ts"` (Node ≥ 22.6 strips TS types itself; no runner, no build step). Single test: `node --test --import ./test/register-loader.mjs test/<name>.test.ts`. `test/register-loader.mjs` + `test/ts-resolve-loader.mjs` resolve the extensionless imports and the `@/` alias, which plain Node cannot.
- Seed: `node scripts/seed-production.mjs` — idempotent courts/hours only, writes `scripts/seed-production.result.json`. Hand-parses `.env` (quotes stripped, no expansion); Next auto-loads `.env` for the app but the seed does not use `dotenv`.
- No ESLint/Prettier/vitest/jest/playwright config. Don't add tooling without asking.

## Setup order

1. Copy `.env.example` → `.env` (keys: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `GMAIL_USER/GMAIL_APP_PASSWORD`, `MAIL_FROM`, `APP_URL`, optional `SMTP_HOST/PORT/SECURE`, Sentry `*_DSN/ORG/PROJECT/AUTH_TOKEN`). `DATABASE_URL` / `DATABASE_POOLER_URL` / `DIRECT_DATABASE_URL` are only used by the seed script and `drizzle-kit`/`pg_dump` — the app itself talks to Supabase over HTTP and never opens a TCP connection.
2. In the Supabase SQL editor, run **in this order**:
   1. `drizzle/*.sql` (the Drizzle-generated migrations — tables, indexes, RLS helper objects). These are generated files; do not edit them. **`drizzle/0005_outbox_claimed_at.sql` adds `email_outbox.claimed_at`; it must be applied before `rpc-functions.sql`, whose `rpc_claim_outbox_batch` writes that column.**
   2. `supabase/proof-bucket.sql` — private `proofs` bucket.
   3. `supabase/audit-rls.sql` — RLS default-deny, no-update/no-delete; service_role bypass.
   4. **`supabase/rpc-functions.sql`** — the core RPCs **and** `holds_court_slot_unique_idx`. This file is the source of truth for anything Drizzle cannot express (`booking_slots_no_overlap_idx` is generated; the holds uniqueness is declared in `schema.ts` but applied here). Re-running it is safe (`CREATE OR REPLACE`, `IF NOT EXISTS`) — it also drops the now-redundant non-unique `holds_court_slot_idx`. Every `SECURITY DEFINER` function here pins `SET search_path = public, pg_temp`; keep that on any new one.
   5. **`supabase/expenses.sql`** — expense table, RLS, and transactional expense CRUD/audit RPCs. Re-running it is safe.
   6. **`supabase/refund.sql`** — `refund_reason` column, the widened `bookings_status_check` (adds `Refunded`), and `rpc_refund_booking`. Required before the Refund button works. Re-running it is safe.
   7. **`supabase/booking-delete.sql`** — `rpc_delete_booking`. Required before the Delete button works. Re-running it is safe.
   8. **`supabase/security-lockdown.sql`** — run this **last**. It enables RLS on all 14 business tables, revokes every table/sequence/function privilege from `anon` and `authenticated`, grants the `rpc_*` functions to `service_role` only, and sets default privileges so a newly created table starts closed. The public anon key ships in the browser bundle, so without this file every table is readable and writable by anyone. The file ends with verification queries — run them and expect the results in the comments (in particular: zero rows for anon-granted tables and zero rows for anon-executable `SECURITY DEFINER` functions, and **exactly one** row for `rpc_claim_outbox_batch` — two means a stale overload survived, see block 2 of `scripts/diagnose-outbox.sql`).
   9. `supabase/outbox-cron.sql` — **optional but recommended.** Hourly outbox drain via `pg_cron` + `pg_net`, because Vercel Hobby cannot run a cron more than once a day. Needs `create extension if not exists pg_cron;` and `pg_net;` first, and you must replace `YOUR-APP-DOMAIN` / `YOUR-CRON-SECRET` in the file. Skipping it is safe: mail still flows, the worst-case delay is just one day instead of one hour.
   To diagnose "no email arrived", run `scripts/diagnose-outbox.sql` (read-only).
3. Run the seed, then `npm run dev` / `npm run build`.
4. Deploy (Vercel primary): set Vercel Production env (`NEXT_PUBLIC_SUPABASE_*`, `SUPABASE_SERVICE_ROLE_KEY`, `GMAIL_USER/GMAIL_APP_PASSWORD`, `MAIL_FROM` real domain, `APP_URL` https prod domain, `CRON_SECRET` same secret for `vercel.json` crons), do NOT set `SMTP_HOST` on Vercel (Gmail path). Build command `npm run build` (default).

**SQL drift is the main hazard in this repo.** The DB is not idempotently derivable from `src/db/schema.ts` alone: everything in `supabase/*.sql` lives only there. If you add an RPC, an index, or a trigger, add it to the matching file in `supabase/` and re-run that file in the SQL editor. Never assume `drizzle-kit migrate` covers it.

Rules for anything new at the DB boundary:
- Every new table needs a line in `supabase/security-lockdown.sql` (`ENABLE ROW LEVEL SECURITY`) **and** must be listed in its verification query. The `ALTER DEFAULT PRIVILEGES` block covers grants, but RLS is per table and is not automatic.
- Every new `SECURITY DEFINER` function needs `SET search_path = public, pg_temp`, a `REVOKE ALL … FROM PUBLIC, anon, authenticated`, a `GRANT EXECUTE … TO service_role`, and a line in the lockdown file's function lists (both the REVOKE/GRANT blocks and the verification query).
- A new column that an RPC writes needs a `drizzle/000N_*.sql` migration applied **before** the `supabase/*.sql` file that uses it.

## Architecture

- Entrypoints: `src/app/layout.tsx` (Geist + `Toaster` from `@/components/ui/sonner`), `src/app/page.tsx` (public booking, `force-dynamic`, `FALLBACK_COURTS=[]` on DB miss), `src/app/{admin,login,register,track/[token]}/page.tsx`, ~34 `src/app/api/**/route.ts` (incl. `src/app/api/cron/*` wired via `vercel.json`), `src/proxy.ts`, `src/instrumentation.ts`.
- Auth: Next 16 **proxy** (`src/proxy.ts`, not `middleware.ts`). Uses `@supabase/ssr` `getClaims()` only — never `getSession()`. Gates `/admin/:path*`, redirects to `/login`. The proxy only proves *a* user is logged in; admin role is enforced per-route by `requireAdmin()` (`src/lib/admin/session.ts`). The proxy also applies per-IP rate limits to the unauthenticated routes — the write routes (`/api/holds`, `/api/holds/reclaim`, `/api/submit`, `/api/proofs/upload-url`, `/api/auth/forgot-password`, `/api/auth/login`) plus the GET tracking look-up (`/api/booking/track`, which is limited because a 5-char code is otherwise brute-forceable). Each rule declares its own `methods`, defaulting to POST/DELETE. This is an in-memory, per-process counter, so the effective limit is `limit × instances`. **A new unauthenticated route must be added to both `WRITE_LIMITS` and the `config.matcher` in `src/proxy.ts`** — a route missing from the matcher is never limited at all.
- DB: **`@supabase/supabase-js` HTTP client only** — no TCP pool, no Drizzle runtime. `getDb()` in `src/db/client.ts` is a service-role singleton that throws `NOT_CONFIGURED` without env so `next build` passes. `src/db/schema.ts` contains Drizzle definitions used for types only (`.$inferSelect`); no query runs through it. Transactional paths live in `supabase/rpc-functions.sql` and `supabase/expenses.sql`:
  - `rpc_submit_booking(...)` — the 18-step submit transaction (idempotency keys, `FOR UPDATE` holds, clash + proof-reuse checks, inserts, outbox rows, audit row).
  - `rpc_apply_decision(...)` — approve/reject, flips slot states, outbox + audit rows.
  - `rpc_claim_outbox_batch(p_limit, p_booking_id)` — `FOR UPDATE SKIP LOCKED` outbox claim. `p_booking_id` (nullable) narrows it to one booking's rows; the inline request paths always pass it, the cron passes NULL. Also reclaims rows stranded in `status='sending'` for more than 15 minutes (a process that died mid-batch would otherwise hold them forever), which is why `email_outbox.claimed_at` exists.
  - `rpc_reclaim_holds(...)` — revives a lapsed hold for the same `owner_token`. Re-checks live bookings `FOR UPDATE` inside the transaction; a taken slot raises `23505` and surfaces as `SLOT_TAKEN`.
  - `rpc_delete_expired_holds(p_cutoff)` — retention purge.
  - `rpc_admin_create_booking(...)` — admin walk-in booking. Evicts live holds only for the (court, slot) pairs it books; it must never delete holds table-wide.
  - `rpc_refund_booking(p_booking_id, p_actor_email, p_reason)` — Approved → Refunded, records the optional note, releases the slots (`state = 'rejected'`), queues `booking_customer_refunded`, writes a `booking.refund` audit row. Finance/revenue key on `status = 'Approved'`, so a refunded booking drops out of every report with no query change. Idempotent.
  - `rpc_delete_booking(p_booking_id, p_actor_email)` — permanent hard delete on any status. Removes `email_outbox` + `idempotency_keys` first (no cascade), snapshots the booking into a `booking.delete` audit row, then deletes the booking (slots/rentals/proofs cascade; slots are freed). Idempotent (`deleted: false`).
  - `rpc_replace_court_hours(...)`, `rpc_add_court_hours(...)`, `rpc_delete_expired_proofs(...)`.
  Every one of these is `SECURITY DEFINER` with `SET search_path = public, pg_temp` and is executable by `service_role` only — see `supabase/security-lockdown.sql`. An anon-executable `SECURITY DEFINER` function bypasses RLS entirely, so a missing `REVOKE` is a full data breach, not a nuisance.
  Overlap guard is the partial unique index `booking_slots_no_overlap_idx WHERE state IN ('held','pending','approved')` (the DB list is deliberately wider than the app's `LIVE_SLOT_STATES`). `holds_court_slot_unique_idx` guards one hold per (court, slot) — plain, not partial, because an index predicate must be immutable and a partial predicate is tested on write only, so it could not have meant "live holds" anyway. Expiry unblocks a slot only via a DELETE: `rpc_submit_booking` purges expired holds, the retention cron purges weekly, and `POST /api/holds` clears the expired rows for the pairs it inserts.
- Mail/outbox: Gmail port 587 + App Password (`src/lib/mail/transport.ts`); `SMTP_HOST` set routes to local Mailpit instead (`127.0.0.1:1025`). Shared lazy transport. `src/lib/mail/*` must NOT import `server-only` (the worker is imported from non-route contexts). Primary delivery is inline and **scoped to that booking**: `drainOutboxWithin(budget, bookingId)` in submit, `drainBookingOutboxBestEffort(id)` in approve/reject/admin-create. Never drain unscoped on a request path — one send costs ~5s on a cold instance, so an unfiltered claim of 50 rows made every booking after the first in a burst time out (the claim takes an optional `p_booking_id` for exactly this). Vercel crons are backstops (`outbox` **daily `5 2 * * *`** — Hobby cannot run more often, `retention` Sun 02:00, `keepalive` daily, `proof-prune` 1st 03:00). The FREQUENT outbox drain is **Supabase `pg_cron` + `pg_net`, hourly**, defined in `supabase/outbox-cron.sql` — that file is what caps mail delay at ~1 hour; Vercel's daily cron alone would let a mid-morning booking sit unsent ~16 hours after payment. If `supabase/outbox-cron.sql` is not run, mail still flows, just with the daily worst case. Do not raise the Vercel schedule above daily on Hobby. One owner alert per batch, not per dead row. A row sits in `status='sending'` between claim and send; the claim function re-queues anything left there over 15 minutes. `after()` on Vercel is best-effort, so treat "the cron will get it" as the real guarantee, not `after()`.
- Cron auth: all four `src/app/api/cron/*` routes share `isCronAuthorized()` in `src/lib/cron/auth.ts`. It fails **closed** — an unset `CRON_SECRET` in production returns 401 rather than opening the endpoint. Do not copy this helper into a route again; import it.
- Sentry: errors-only (`tracesSampleRate:0`, no replay), silent no-op if DSN missing. `next.config.ts` skips `withSentryConfig` unless `SENTRY_AUTH_TOKEN` set — build passes without it.
- Styling: Tailwind v4.3 CSS-first (`@theme` in `src/app/globals.css`, single `@tailwindcss/postcss` plugin, no config file). Components under `src/components/ui` were scaffolded by the **shadcn CLI** (`npx shadcn@latest add … -b base`, `components.json` is its config) — the `shadcn` package is a CLI, **not** a dependency, and `@import "shadcn/tailwind.css"` was removed from `globals.css` because the published `shadcn@1.0.0` ships no CSS. RSC, `lucide-react` named imports, `cn()` from `@/lib/utils` (the `cn` npm package — a drop-in for clsx + tailwind-merge, so neither is a dependency).
- Timezone: `Asia/Manila`. Never do browser-local date math. The Manila helpers live in `src/lib/booking/slots.ts` (`manilaDateStr`, `selectionDateStr`, `isOnSlotGrid`, `isFutureSlot`, `isWithinBookingHorizon`, `maxBookableInstant`) and `src/lib/courts.ts` (display formatting only, and it re-exports the slot helpers rather than duplicating them). Slot grid: 24 hourly slots from 00:00 Manila — court operating hours (`operating_hours`, admin-configurable, equal open/close = 24 h) decide which are bookable, `MAX_SLOTS_PER_BOOKING` 12, holds expire after `HOLD_TTL_MINUTES` 10.
- Server-side limits are enforced in `src/lib/booking/validation.ts`, never trusted from the client: 12-month booking horizon, slot count, hold token shape, proof size/mime.

## Conventions / gotchas

- Customer tracking needs **code + email** (`/api/booking/track`): the 5-char code is single-factor by itself.
- Vercel needs `nodejs` runtime + `force-dynamic` on DB/mail routes (already in code); `proxy.ts` stays off `nodejs`.
- Don't edit generated/artifacts: `.next/`, `node_modules/`, `tsconfig.tsbuildinfo`, `next-env.d.ts`, `drizzle/*.sql` + `drizzle/meta/*`, `scripts/seed-production.result.json`.
- Frozen context in `docs/DECISIONS.md` (ADR-01..10: rates/hours/auth/email/storage) and `docs/BACKUPS.md` (manual `pg_dump` runbook). `docs/OPEN-QUESTIONS.md` has no open questions.
- **Never drive a browser to verify a change** — no Playwright, Chrome DevTools, headless screenshots, or the OpenChamber browser panel. There is no standing permission: ask the user first, every time, and wait for a yes (a yes covers that one request only). The user verifies UI in their own browser. `npm run dev` + `curl`/server-side HTTP checks need no permission.
- Manual end-to-end verification still needs live Supabase Postgres + Auth/Storage and a Gmail App Password or Mailpit; `npm test` covers only the pure pricing/hours functions. That pass is the user's to run — ask them to do it rather than driving a browser yourself.
